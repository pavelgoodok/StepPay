# Архитектура StepPay

## Слои

1. packages/engine - чистые функции над состоянием (State): кошельки, сделки, этапы, споры, журнал с хеш-цепочкой, хеш контракта, якоря, абстракция платежного контура (MoneyRail). Не знает про сеть, базу и пользователей. Все суммы в копейках.
2. apps/api - Fastify. Хранит единственный экземпляр State в памяти, каждое изменение проходит через transact (очередь, один писатель): применить функцию движка, сохранить в хранилище, только затем заменить state. Хранилище: MemoryStore или PgStore (jsonb).
3. Platform (platform.ts) - данные вокруг сделок, которых нет в движке: услуги, проекты, чаты, отзывы, уведомления, якоря, данные зеркала сети.
4. Directory (users.ts) - пользователи, режим личный или профессиональный, ключи и passkey, сессии.
5. ChainMirror (chain.ts) - после каждого transact повторяет записи журнала в контракте StepEscrow (Sepolia) от имени кошельков пользователей. Источник истины остается в движке, сеть подтверждает.
6. Hub (hub.ts) - SSE: события changed (обновить экран) и notify (текст). Каждое notify через sink записывается в раздел уведомлений.
7. apps/web - Next.js. lib/session.tsx держит профиль и счетчики, lib/api.ts вызывает API, usePoll и SSE обновляют экраны.

## Путь одного действия (принятие этапа)

web: POST /deals/:id/approve/:stageId -> app.ts act() -> approveStage (engine) -> transact: store.save, state = next, mirror.notify -> announce(): hub.send notify и changed -> sink сохраняет уведомление -> web получает changed и перечитывает сделку. Параллельно ChainMirror.sync отправляет транзакцию approve в StepEscrow.

## Права по режимам

Личный аккаунт (kind customer): видит заказы, откликается, ведет сделки как заказчик; создание услуг и проектов закрыто (proOnly в routes-platform.ts). Профессиональный (kind executor): создает услуги и проекты, выступает исполнителем. Отзывы возможны только о исполнителе и только после взаимодействия, один раз на пару; рейтинг - среднее по оценкам.

## Известные ограничения

- Состояние одного экземпляра API держится в памяти и целиком пишется в jsonb при каждом изменении: масштабирование только вертикальное, несколько реплик дадут расхождение state и SSE.
- Hub хранит соединения в памяти процесса.
- Ограничитель частоты запросов тоже в памяти процесса.
- Серверная подпись контракта (HMAC) - демо-режим, в рабочем режиме нужен signaturePolicy device или passkey.
- ChainMirror: отправка в сеть асинхронна, расхождение показывает reconcile и verify.

## Масштабирование: этапы

1. Выполнено: единственный пишущий экземпляр. API берет блокировку Postgres (pg_try_advisory_lock) на отдельном соединении; при выкладке новая версия ждет, пока старая завершится, и не затирает ее запись.
2. Далее: вынести сделки, журнал, пользователей и уведомления из одного jsonb в таблицы с блокировкой на уровне сделки.
3. Далее: SSE между репликами через LISTEN/NOTIFY, счетчик запросов в базе.
4. Далее: несколько реплик API при чтении, одна при записи.
