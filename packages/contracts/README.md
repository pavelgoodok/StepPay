# StepEscrow: эталонный смарт-контракт

Контракт на Solidity повторяет логику ядра сделок (`packages/engine`): резерв, подписи сторон, выплата по принятым этапам, возврат остатка, голосование спонсоров, спор с приемщиком, автоприемка, комиссия. Он показывает, что механика переносится на любую платформу программируемых денег. В продукте деньги сейчас эмулируются, контракт к ним не подключен.

## Запуск

```bash
pnpm install
pnpm --filter @steppay/contracts test              # сценарии контракта и сравнение с ядром, ~10 секунд
pnpm --filter @steppay/contracts test:invariants   # случайные действия с проверкой инвариантов, ~1 минута
pnpm --filter @steppay/contracts test:differential # случайные сценарии против ядра сделок, ~10 секунд (FC_DIFF_RUNS=400 для глубокой проверки)
```

Компилятор берется из npm-пакета `solc` (solcjs версии 0.8.28), бинарники из интернета не скачиваются. Сети не нужно: тесты идут на встроенной сети Hardhat.

## Соответствие ядру

| Ядро | Контракт |
|---|---|
| Режимы `own`, `crowdfunding`, `grant` | `Mode.Own`, `Mode.Crowdfunding`, `Mode.Grant` |
| Контракт и хеш условий (шаг 1) | `contractHash` хранится в сделке и событии `DealCreated`: хеш из ядра можно сверить с цепочкой |
| Подписи сторон (шаг 3) | `sign`: исполнитель и заказчик, у краудфандинга только автор; работа начинается после резерва и подписей |
| `fund` | `fund`: заказчик вносит всю сумму, спонсоры любые взносы до цели; токены списываются через `approve` |
| `approveStage`, `rejectStage` | то же имя; отказ в личной сделке открывает спор, в гранте проваливает этап |
| `voteStage` | `vote`: вес голоса равен взносу, больше половины «за» принимает, половина и больше «против» проваливает |
| `openDispute`, `resolveDispute` | то же имя, решает только приемщик |
| `tick` | `autoAccept`: после срока этап принимает любой желающий |
| `expireFunding`, `expireStage`, `expireDispute` | то же имя, сроки задаются в `createDealEx`, вызвать выход по сроку может любой |
| запасной приемщик | `createDealFull`, `resolveDispute` пускает запасного со второй половины срока на спор |
| `splitProRata` | `_split`: метод наибольших остатков, ничего не теряется |
| `cancelDeal` | `cancel`: заказчик, у краудфандинга автор, нельзя при этапе на приемке или в споре |

Отличия: журнал событий ядра заменен событиями контракта; описание работ и фото лежат вне цепочки, на цепочку попадает только хеш материалов; статус «Согласование» (черновик) живет на платформе, в контракт сделка попадает с готовыми условиями.

## Инварианты

Проверяются после каждого действия в случайных прогонах:
1. Баланс токенов контракта равен `totalLocked` (сумме резервов всех сделок).
2. `totalLocked` равен сумме резервов по сделкам, а резервы каждой сделки совпадают с `totalReserved` внутри нее.
3. Завершенная или отмененная сделка не держит резервов.
4. В активной сделке резерв равен сумме непринятых этапов.
5. Токены не создаются и не пропадают: сумма балансов участников и контракта постоянна.
6. Этапы идут по порядку: принятые, не больше одного в работе, остальные ждут.

Проверка на мутациях: если убрать списание `totalLocked` при выплате или обнуление резерва при возврате, прогон падает на первых десятках действий.

## Прогон в тестовой сети

```bash
pnpm --filter @steppay/contracts chain:local      # локально, без ключей, результат в reports/
SEPOLIA_RPC_URL=... DEPLOYER_PRIVATE_KEY=0x... pnpm --filter @steppay/contracts chain:sepolia
```

Ключ берется только из переменной окружения. Подробности и привязка отчета к сделке платформы в `docs/smart-contracts.md`, шаг 6.

## Что не проверено

Контракт не проходил независимый аудит. Токен предполагается обычным ERC-20 без комиссий при переводе и без хуков. Тестовые токены тестовой сети не имеют стоимости. Подключение к денежному рельсу и тестовая сеть это шаги 5 и 6 плана.
